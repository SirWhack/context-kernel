# Regenerate materialized files via pre-commit git hook, not read-time gate

**Status:** accepted (supersedes [ADR-0003](./0003-pull-based-jit-regeneration.md))
**Date:** 2026-05-24

Materialized documentation (`AGENTS.md`, `CLAUDE.md` bridge) is regenerated by a git `pre-commit` hook that runs `ck ingest && ck materialize --all` and stages the updated files. Documentation is committed alongside the code that produced it. No runtime freshness gate, no daemon, no file watcher.

The staleness window is bounded by commit frequency. Uncommitted edits are not reflected in materialized files until the next commit. This is acceptable because regular git usage throughout the day keeps documentation fresh — and because the documentation is a committed artifact, human readers and agents both see the same consistent state.

## Why ADR-0003 was superseded

ADR-0003 committed to pull-based JIT regeneration: a `PreToolUse` hook intercepted every agent read and triggered regeneration on hash mismatch. This made stale reads structurally impossible for agents — but left a gap: human reads (IDE browsing, `cat`, code review) were unprotected.

The pre-commit model closes that gap. Everyone — agents, humans, CI, code review — reads the same committed state. The "errors out of existence" property shifts from the read boundary to the commit boundary: you cannot commit code without its documentation being in sync.

## Considered options

All options from ADR-0003 remain considered. The new option:

- **Pre-commit git hook.** Regeneration runs before every commit; updated materialized files are staged automatically. No daemon, no runtime interception, no read-time latency cost. Trade-off: uncommitted edits are not reflected until commit. Accepted because regular git workflow (commit early, commit often) keeps the window small, and the documentation is useful primarily in its committed form (for code review, branch checkout, collaboration).

## Consequences

- Materialized files are version-controlled. `git checkout feature-branch` gives you documentation matching that branch's code.
- No `PreToolUse` hook integration needed. FreshnessGate remains as a module (`ck check` still works for manual verification) but is no longer the enforcement mechanism.
- Pre-commit hook adds a few seconds to every commit (incremental ingest + materialize). Acceptable per S0 latency measurements (~10s worst case on cold scope; sub-second on unchanged files).
- Code review includes generated documentation diffs — reviewers see how code changes affect the orientation context.
- The hook is git-specific but not Claude-Code-specific. Any agent or editor that commits via git gets the same freshness guarantee.

## When this should be revisited

- If pre-commit latency becomes painful on large portfolios (hundreds of scopes, thousands of files). May need to scope regeneration to changed scopes only rather than `--all`.
- If a use case emerges where uncommitted-edit freshness matters (e.g., a long coding session without commits where the agent needs up-to-date orientation). Could add `ck check` as an optional manual refresh without reverting to the full read-time gate.
- If `.context-kernel/` is committed to git (open question in THEORY.md), the hook may need to stage those files too.
