# S4 — Deepen Ingester: TypeScript/JS handler

**Status:** spec complete, ready to build.
**[PLAN.md](../../PLAN.md) reference:** §S4.
**Authors of this spec:** decisions from `/grill-with-docs` session on 2026-05-25.

## Goal

A `TypeScriptHandler` that extracts module, class, and function entities from TypeScript and JavaScript source files using tree-sitter, with Ousterhout-informed structured descriptions matching PythonHandler's format. Plugs into the existing `ingest()` orchestration from S3.

## In scope

- `TypeScriptHandler` implementing `StructuredHandler` protocol
- Supports `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs` — one handler, grammar selection internal
- Same three entity kinds as PythonHandler: `module`, `class`, `function`
- TS-specific constructs fold into existing kinds: `interface` → `class`, `enum` → `class`, `type` alias → module preamble
- Export keyword as visibility signal (not `_`-prefix convention)
- Static import extraction (`import`, `require()`, re-exports); dynamic `import()` skipped
- Arrow functions and function expressions assigned to `const`/`let` detected as `function` entities
- Type annotations extracted from source text (no resolution, no normalization)
- No special React/JSX component treatment — function components are functions, class components are classes
- tree-sitter as the parser (pip packages: `tree-sitter`, `tree-sitter-typescript`, `tree-sitter-javascript`)

## Out of scope (deferred)

| Concern | Where |
|---|---|
| Cross-scope frontend↔backend relationship detection | EntityResolver (ARCHITECTURE.md §6) or LightRAG entity merging |
| Embedding for TS/JS sources | S5 (`find` design determines embedding strategy for code) |
| `.d.ts` declaration file support | Future; same handler would work, but not tested in S4 |
| CommonJS `module.exports` pattern detection | Best-effort only; not all patterns covered |
| Decorators as semantic signals | Future; tree-sitter parses them but we don't interpret |

## Concrete specs

### Handler: `TypeScriptHandler`

Single handler class. `supports()` checks suffix against `{.ts, .tsx, .js, .jsx, .mjs, .cjs}`. Internally selects grammar: TypeScript for `.ts`, TSX for `.tsx`, JavaScript for `.js`/`.jsx`/`.mjs`/`.cjs`.

### Parser: tree-sitter

- `tree-sitter-typescript` provides `language_typescript()` and `language_tsx()`
- `tree-sitter-javascript` provides `language()`
- Source text is read as bytes, parsed into a CST, entities extracted by walking top-level nodes

### Entity kinds

Same three as PythonHandler. TS-specific constructs fold:

| TS/JS construct | Entity kind | Notes |
|---|---|---|
| `class` declaration | `class` | Same as Python |
| `interface` declaration | `class` | Structurally identical — name, members, inheritance |
| `enum` declaration | `class` | Named set of members |
| `function` declaration | `function` | Same as Python |
| Arrow fn / fn-expression assigned to `const`/`let` | `function` | Detect initializer node type |
| `type` alias | Module preamble | Like Python constants |
| File itself | `module` | One per file |

### Visibility: export keyword

- `export` keyword on a declaration → Interface (public)
- No `export` → Internals (private)
- `export default` → Interface, noted as default export
- Class members: `private`/`protected` accessibility modifier → Internals; `public` or no modifier → Interface

### Import extraction

Static forms produce `imports` relationships:

- `import { X } from './path'` → imports `./path.X`
- `import * as X from './path'` → imports `./path`
- `import X from './path'` (default) → imports `./path`
- `require('./path')` (CommonJS) → imports `./path`
- `export { X } from './path'` (re-export) → imports `./path.X` + listed in exports
- Side-effect `import './path'` → imports `./path`
- Dynamic `import()` → skipped

### Description format

Mirrors PythonHandler's Ousterhout-informed format:

**Module:**
```
Module: src/services/foo.ts
  Docstring: (first comment block if present)

  Exports:
    MyService (class), helper, standalone

  Private:
    _internal, _CACHE_SIZE

  Imports:
    ./bar.Foo, ./baz

  Depth: 3 exports, 2 private, 85 LOC
```

**Class/Interface/Enum:**
```
Class: MyService
  File: src/services/foo.ts

  Interface:
    name: string
    run(x: number): Promise<void>

  Internals:
    _cache: Map<string, number>
    _doWork(x: number): Promise<void>

  Depth: 2 public methods, 1 private method, 25 LOC
  Bases: IService (implements)
```

**Function:**
```
Function: helper(x: string): number
  File: src/services/foo.ts
  Visibility: public
  Depth: 5 LOC
```

### Syntax errors and edge cases

- Parse errors: skip file with warning (same as PythonHandler)
- Empty files: no entities
- Files with only type aliases / imports: module entity only (type aliases in preamble)

## Verification

1. `TypeScriptHandler.supports()` returns `True` for `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`; `False` for `.py`, `.md`.
2. Extract on a `.ts` file with a class produces `module` + `class` entities.
3. Extract on a `.js` file with functions produces `module` + `function` entities.
4. Class entity descriptions include Interface/Internals split based on accessibility modifiers.
5. Class entity descriptions include depth metrics (LOC, method counts).
6. Interfaces are extracted as `class` kind with correct Interface section.
7. Enums are extracted as `class` kind with members listed.
8. Arrow functions assigned to `const` produce `function` entities.
9. Export keyword determines visibility — exported = public, non-exported = private.
10. Import relationships extracted for static import forms.
11. Type annotations preserved in signatures from source text.
12. `.tsx` files parse correctly (JSX syntax doesn't break extraction).
13. Syntax errors skip with warning, not crash.
14. Empty files produce no entities.
15. Entity IDs are deterministic: same file parsed twice → same IDs.
16. `ingest()` processes TypeScriptHandler sources alongside PythonHandler sources.
