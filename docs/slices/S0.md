# S0 — LightRAG validation spike

**Status:** queued. Handed off to a separate research/spike agent on 2026-05-23. PLAN.md will be updated to insert S0 above S1 when results land.
**Authors of this spec:** decisions from `/grill-with-docs` sessions on 2026-05-23 and 2026-05-24.

## Why S0 exists

PLAN.md S1 (walking skeleton) assumes a working LightRAG end-to-end. [ARCHITECTURE.md](../../ARCHITECTURE.md) §1.1.1 already required LightRAG validation on the 7900 XTX *before* commitment — that validation has not happened. S0 is the de-risking spike that produces a go/no-go on four questions:

1. Does LightRAG ingest + query work on a representative corpus at all?
2. Which indexing LLM wins on the 7900 XTX for this workload?
3. Is the first-read latency proxy under 60s? (Threshold from [THEORY.md](../../THEORY.md) open question 3.)
4. Does the resulting graph have non-sparse cross-scope relationships? (Threshold from [THEORY.md](../../THEORY.md) open question 4 + [ADR-0009](../adr/0009-cross-scope-relationships-via-source-id.md).)

If any of (1)-(4) fails on the chosen backend, that is a signal to re-grill [`ADR-0004 LightRAG`](../adr/0004-switch-to-lightrag.md) or `THEORY.md` open question 3. It is cheaper to learn this in a throwaway spike than after the walking skeleton has been built around the assumption.

## Open branches to confirm before running

These need the operator's yes/no before the spike script is written:

### (a) Which indexing LLMs to benchmark?

Two MoE candidates side-by-side on the same corpus:

1. **Qwen3-30B-A3B-Instruct-2507** @ Q4_K_M, 64K ctx, Q8 KV, flash attention. Baseline — LightRAG shipped Sept 2025 entity-extraction tuning for this exact model.
2. **Qwen3.6-35B-A3B** @ UD-IQ4_XS (~17.7 GB), 64K ctx, Q8 KV, `enable_thinking=False`. Challenger — released 2026-04-16. **Footgun:** unified hybrid-thinking design has reports of think-tag leakage in llama.cpp ([issue #22398](https://github.com/ggml-org/llama.cpp/issues/22398)). The LM Studio chat template must suppress thinking on every call before extraction is trustworthy.

Gemma 4 31B dropped from S0; comparator only if both Qwen variants disappoint on extraction quality.

### (b) Which embedder?

Pending the research handoff outcome — see below.

### (c) Embedder placement

Separate `llama-server` (or LM Studio second slot) on a different port. Co-resident on the GPU since the MoE LLM only uses ~18-22 GB and either embedder candidate is ≤2 GB.

### (d) Exit criteria — what the spike must produce

1. **Single-file Python script** (not yet the `ck` AgentCLI shape) that runs LightRAG ingest + a representative query end-to-end against ~50 markdown files.
2. **Per candidate model:** ingest wall-time, tok/s during ingest, peak VRAM, extracted entity count, spot-check of 3-5 chunks for extraction correctness.
3. **First-read latency proxy:** wall-time to materialize one scope's worth of summary content from the graph. The number [ADR-0003](../adr/0003-pull-based-jit-regeneration.md) lives or dies on. **Threshold: < 60s** per [ARCHITECTURE.md](../../ARCHITECTURE.md) §7.
4. **Cross-scope relationship density** (per [ADR-0009](../adr/0009-cross-scope-relationships-via-source-id.md)): count of relationships whose endpoints span ≥2 scopes (source-files in different directories), expressed as a fraction of total relationships. **The number [THEORY.md](../../THEORY.md) open question 4 lives or dies on — and with it, the thesis.** Thresholds: **≥15%** = go; **<5%** = stop and re-grill [ADR-0004](../adr/0004-switch-to-lightrag.md); **5-15%** = limp forward with caveat and watch closely.
5. **Go/no-go on:** (i) does LightRAG work, (ii) which model wins, (iii) is first-read latency <60s, (iv) is cross-scope density ≥15%.

### (e) Spike location

Throwaway `spike/` directory at the project root. Not inside any future v1 module layout — this is proving the dependency, not building the architecture.

## Empirical findings worth carrying forward (from the 2026-05-23 grill)

- **MoE wins on the 7900 XTX.** Dense 30B Q4_K_M (~17 GB) is memory-bandwidth-bound at ~15-20 tok/s. Qwen3 / 3.6 MoE with ~3B active reads ~2 GB per token → ~80-100 tok/s. For an ingest workload of hundreds-to-thousands of LLM calls, this is the whole game.
- **Gemma 3/4 hybrid sliding-window attention** (5:1 local:global, 1024-token local window) cuts KV cache by ~5× vs. the naive formula. Gemma 4 31B @ 100K context Q8 KV actually fits (~20-21 GB), contradicting the earlier ~28 GB estimate. Lesson: trust empirical reports over per-layer math when SWA / GQA is in play.
- **bge-m3 stickiness reminder:** LightRAG requires nuking the vector storage to switch embedders. Whatever the spike commits to becomes load-bearing for any subsequent re-ingest until `rm -rf .context-kernel/`.
