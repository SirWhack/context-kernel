## Why S0 exists

PLAN.md S1 (walking skeleton) assumes a working LightRAG end-to-end. [ARCHITECTURE.md](../../ARCHITECTURE.md) §1.1.1 already required LightRAG validation on the 7900 XTX *before* commitment — that validation has not happened. S0 is the de-risking spike that produces a go/no-go on four questions:

1. Does LightRAG ingest + query work on a representative corpus at all?
2. Which indexing LLM wins on the 7900 XTX for this workload?
3. Is the first-read latency proxy under 60s? (Threshold from [THEORY.md](../../THEORY.md) open question 3.)
4. Does the resulting graph have non-sparse cross-scope relationships? (Threshold from [THEORY.md](../../THEORY.md) open question 4 + [ADR-0009](../adr/0009-cross-scope-relationships-via-source-id.md).)

If any of (1)-(4) fails on the chosen backend, that is a signal to re-grill [`ADR-0004 LightRAG`](../adr/0004-switch-to-lightrag.md) or `THEORY.md` open question 3. It is cheaper to learn this in a throwaway spike than after the walking skeleton has been built around the assumption.

## Resolved branches

### (a) Indexing LLMs benchmarked — resolved 2026-05-24

Two MoE candidates against the same corpus:

1. **Qwen3-30B-A3B-Instruct-2507 Q4_K_M** — baseline. Non-thinking by default; LightRAG-validated in the public record; 94 tok/s decode measured.
2. **Qwen3.6-35B-A3B-MTP UD-IQ4_NL** — challenger. MTP via upstream master's `--spec-type draft-mtp`. Forced into non-thinking via `--reasoning off`. 109-121 tok/s decode measured (1.16-1.29× faster than Qwen3-30B).

Per [docs/research/S0_llm.md](../research/S0_llm.md): the regular non-MTP Qwen3.6-35B Q4_K_M variant at 22+ GB is a budget inversion and was rejected. UD-IQ4_NL on the MTP repo (18.5 GB) is the only Qwen3.6 variant that fits 24 GB once an embedder is co-resident. Qwen3.6-27B dense was researched and skipped — ~3× slower (dense vs A3B MoE) and the structured-output silent-corruption flag from RTX 4090 recipes is a risk on the MTP path. Gemma 4 31B dropped.

### (b) Embedder — resolved 2026-05-24

**Qwen3-Embedding-0.6B Q8_0**, per [docs/research/S0_embed.md](../research/S0_embed.md): MTEB English Retrieval 61.83 vs bge-m3 ~58; Apache 2.0; 32K context. bge-m3 retained as conservative fallback.

Operational notes:
- **Asymmetric prompts are required** for asymmetric retrieval — `Instruct: ...\nQuery: ...` for queries; plain text for passages. The model card says missing the prefix costs 1-5% retrieval. The spike currently encodes passages plain and does not (yet) prefix queries.
- **LightRAG's `openai_embed` forces `dimensions=1536`** via a decorator — incompatible with Qwen3-Embedding's 1024 dim. The spike bypasses with a direct httpx POST. S1's embedder adapter must do the same or wrap differently.
- Pooling: `last` (last-token pooling), L2-normalized output. Verified at runtime.

### (c) Embedder placement — resolved 2026-05-24

Co-resident on the 7900 XTX, separate `llama-server` process on port 8081. Validated end-to-end: Qwen3.6-MTP @ 16K ctx / parallel 1 plus embedder = 23.9 GB / 24.0 GB VRAM. The card is **fully saturated**; raising LLM context above 16K, parallelism above 1, or switching to a bigger embedder will OOM.

### (d) Exit criteria — what the spike must produce

1. **Single-file Python script** ([spike/spike.py](../../spike/spike.py)) that runs LightRAG ingest + a representative query end-to-end against a real source-code corpus (LifeStrands, ~41 files in the trimmed first pass: `services/chat-service` + `shared` + root markdowns).
2. **Per candidate model:** ingest wall-time, extracted entity/relationship counts, spot-check of 3-5 chunks for extraction correctness.
3. **First-read latency proxy:** wall-time for the spike's `synthesize <scope>` command — gather one scope's entities + within-scope relationships + cross-scope relationships from the graph and send to the LLM with an S1-style synthesis prompt. **Threshold: < 60 s** per [ARCHITECTURE.md](../../ARCHITECTURE.md) §7.
4. **Cross-scope relationship density** (per [ADR-0009](../adr/0009-cross-scope-relationships-via-source-id.md)): for each relationship in the graph, take the union of scopes of both endpoint entities' source `file_path`s; cross-scope if cardinality > 1. **The number [THEORY.md](../../THEORY.md) open question 4 lives or dies on — and with it, the thesis.** Thresholds: **≥ 15 %** = go; **< 5 %** = stop and re-grill [ADR-0004](../adr/0004-switch-to-lightrag.md); **5-15 %** = limp forward with caveat and watch closely.
5. **Go/no-go on:** (i) does LightRAG work, (ii) which model wins, (iii) is first-read latency < 60 s, (iv) is cross-scope density ≥ 15 %.

### (f) Corpus — resolved 2026-05-24

The S0.md plan originally specced "~50 markdown files" but the user's actual portfolio is source-heavy. Reframed: the kernel's job is to *generate* markdown *from* code, so the spike must test exactly that.

**Selected corpus:** `/home/swynn/Code/LifeStrands` — 7-microservice FastAPI + Python project, ~114 candidate files (`*.py`, `*.md`, `*.sql`) across 25 scopes after excluding `venv/`, `node_modules/`, `__pycache__/`, bundled deps (`Orpheus-FastAPI/`, `dia/`, `test-env/`), and `tests/`. Trimmed for the first measurement pass via `INCLUDE_PREFIXES=services/chat-service:shared` to ~41 files / 11 scopes — keeps ingest time tractable while still spanning multiple scopes (necessary for ADR-0009 to be measurable).

## Empirical findings worth carrying forward (from the 2026-05-23 grill)

- **MoE wins on the 7900 XTX.** Dense 30B Q4_K_M (~17 GB) is memory-bandwidth-bound at ~15-20 tok/s. Qwen3 / 3.6 MoE with ~3B active reads ~2 GB per token → ~80-100 tok/s. For an ingest workload of hundreds-to-thousands of LLM calls, this is the whole game.
- **Gemma 3/4 hybrid sliding-window attention** (5:1 local:global, 1024-token local window) cuts KV cache by ~5× vs. the naive formula. Gemma 4 31B @ 100K context Q8 KV actually fits (~20-21 GB), contradicting the earlier ~28 GB estimate. Lesson: trust empirical reports over per-layer math when SWA / GQA is in play.
- **bge-m3 stickiness reminder:** LightRAG requires nuking the vector storage to switch embedders. Whatever the spike commits to becomes load-bearing for any subsequent re-ingest until `rm -rf .context-kernel/`.
