# Recommendations — Context Kernel features and changes

**Date:** 2026-06-09
**Status:** Proposed — each item is an ADR/spec candidate, sequenced for build order
**Basis:** [REVIEW-FABLE.md](./REVIEW-FABLE.md) + the three research documents under
[docs/research/](../research/). Every recommendation cites its evidence there; this
document is the *what to build*, those are the *why to believe it*.

Conventions: each item lists **What / Why / Design / Touches / Accept / Effort / Risks**.
Effort is relative (S < M < L), single-operator. Items are numbered in recommended build

they are as load-bearing as the positive ones.

## R1. Edge-derived sections in AGENTS.md — make the graph visible where agents read

**What.** Deterministically render the graph's edges into each scope's AGENTS.md as four new
sections, generated by pure functions (no LLM): dependencies, dependents, governing decisions,
concepts.

**Why.** The thesis-load-bearing structure (cross-scope edges, doc↔code links) currently never
appears in materialized output — the graph is "nearly inert" at read time (ADR-0023's own
diagnosis, equally true at materialize time). Subject-grouped markdown lists are the
best-performing graph serialization for LLM comprehension (KG-LLM-Bench: up to 17.5 pts format
effect; Turtle/JSON-LD worst). Non-redundant *structural* facts are exactly the content class
that helps, where generated prose restating code hurts (ETH AGENTS.md study: human-specific
content +4 pts, redundant generated content −0.5 to −2 pts). See
[hierarchical-materialization §3](../research/2026-06-09-hierarchical-materialization-and-importance-ranking.md).

**Design.**
- New module `context_kernel/materializer/sections.py`, pure functions taking
  `(scope, entities_by_scope, relationships)` already available from
  `KnowledgeStore.list_entities_by_scope()` / `list_relationships()`:
  - `render_dependencies(scope, …) -> str` — outgoing structural edges (`imports`, `calls`,
    `inherits`) whose **target scope ≠ source scope**, grouped by target scope:
    `- `context_kernel/graph/` — uses `KnowledgeStore`, `Entity` (protocol.py)`.
  - `render_dependents(scope, …) -> str` — the reverse direction ("Used by").
  - `render_decisions(scope, …) -> str` — semantic edges (`realizes`, `governed-by`,
    `addresses`) from this scope's code entities to nodes whose source tier is
    ADR/THEORY/ARCHITECTURE: `- `freshness_gate.py` realizes [ADR-0010](…) — pre-commit
    regeneration`.
  - `render_concepts(scope, …) -> str` — concept hubs with `implemented-by`/`manifested-by`
    anchors in this scope, each with its CodeSpan receipt (`file:line — primitive`, line
    derived at render per ADR-0018).
- Selection: rank entries by `edge_weight × target.confidence`, cap per section
  (`materializer.max_section_entries`, default 8), drop empty sections.
- Section order in the file (Lost-in-the-Middle: load-bearing first, never middle):
  freshness header → pinned blocks → summary prose → **Governing decisions** → **Depends on /
  Used by** → **Concepts** → reference/gap footer.
- Every entry ends in a relative file path — pointers for progressive disclosure, never inlined
  content.

**Touches.** `materializer/sections.py` (new), `materializer/templates.py`
(`render_agents_md` gains section args), `materializer/__init__.py` (pass graph reads through),
tests with `_FakeStore`.

**Accept.** `context_kernel/ingester/`'s AGENTS.md names `graph/` under *Depends on* and lists
ADR-0017 under *Governing decisions*, regenerated idempotently; no LLM calls added; section
content is byte-identical across repeated materializations of the same `graph_commit`.

**Effort.** S–M. **Risks.** Token growth per file — mitigated by caps and R10's path budget.

## R2. `ck eval` — the harness everything else is gated on

**What.** A private, portfolio-specific paired evaluation: `ck eval` runs a question suite
through two arms (kernel-on vs. agentic-grep baseline), scores deterministically where
possible, and reports paired-bootstrap significance plus cost.

**Why.** At least four accepted surfaces are tuned by intuition (edge weights, hop decay,
similarity threshold 0.82, authority tiers); ADR-0023 ships default-on and UNVALIDATED; R4,
R7, R8 below all require measurement before agent-facing exposure. The bar to beat is strong
agentic grep (GrepRAG: naive lexical retrieval ≈ graph baselines), and public benchmarks are
contaminated/defective (SWE-bench Verified: 59.4% of o3-failures had task defects). See
[hierarchical-materialization §4](../research/2026-06-09-hierarchical-materialization-and-importance-ranking.md).

**Design.**
- `evals/suite.yaml`: ~50–100 entries —
  `{id, question, altitude: file|scope|project|portfolio, kind: locate|orient|why,
  gold: {paths: [...], symbols: [...]}, notes}`.
- **Gold-set mining (re-enactment):** a script walks `docs/adr/*.md` + closed issues, maps each
  to the files/methods its implementing commits changed (`git log --name-only` over the merge
  window) — free ground truth for `locate` and `why` questions, the feature-location field's
  standard method.
- Arms: (a) kernel — agent session with materialized tree + MCP `find`; (b) baseline — same
  agent, `.context-kernel/` masked, Read/Grep/Glob only. Same model, same harness, same budget.
- Metrics: file/symbol hit-rate@k against gold (deterministic, primary); tokens in/out, tool
  calls, wall-clock per question (extend `LLMMetrics` to the read side); LLM judge only for
  `orient` questions — answers blinded, order-swapped, reference-guided, one fixed judge config.
- Stats: paired bootstrap over questions (10k resamples, 95% CI); report per-altitude splits.
- Output: `evals/runs/<date>-<label>.md` (the existing convention).

**Touches.** `context_kernel/eval/` (new), `agent_cli.py` (`ck eval`), `evals/` (suite + gold
miner), reuse `scripts/h2_eval.py` / `expansion_ab.py` patterns.

**Accept.** One full run on the 3-project portfolio producing hit-rates, costs, and CIs for
kernel vs. grep; ADR-0023's expansion flag re-measured under it; runs are reproducible from a
pinned config.

**Effort.** M–L (the gold miner is the bulk). **Risks.** Suite overfitting — refresh questions
from real session transcripts quarterly.

## R3. Hierarchical scope summarization — build the altitude axis

**What.** Phase 4 composes summaries bottom-up over the directory tree: leaf scopes from
entity descriptions (as today); parent scopes from **child scope summaries + parent-local
entities**; project and portfolio roots from their children.

**Why.** The thesis is altitude composition; today every summary is flat and independent.
Evidence says this works and compresses hard: RAPTOR sustains ~0.28 summary/children ratio
with quality gains and **measured 4% node-level hallucination with zero upward propagation**;
GraphRAG root summaries at 2.3–2.6% of corpus tokens still win 72% of comprehensiveness
comparisons; every repo-level system composes over the directory tree, none over semantic
clusters. See
[hierarchical-materialization §1](../research/2026-06-09-hierarchical-materialization-and-importance-ranking.md).

**Design.**
- `_process_scope` gains a topological pass: process scopes deepest-first; a parent's prompt
  input = its children's **summary texts** (not file lists) + its own direct entities, ranked
  by R4's importance (until then, `ranking_weight`).
- **Caching composes for free** if and only if the prompt is built from child summary content:
  unchanged child text → unchanged parent prompt → content-addressed cache hit. No new cache
  machinery.
- New summarizer prompt variant for non-leaf scopes: "Given summaries of child scopes and
  local entities, write the parent orientation: shared purpose, how children divide the
  responsibility, cross-child seams." Target ~3–4× compression per level; budget 300–500
  tokens unchanged.
- **Mechanical verification (decompose-then-verify, mechanized):** post-generation, extract
  backtick-quoted identifiers and path-like tokens from the summary; every one must appear in
  the scope's entity-name set ∪ child-scope names ∪ source paths. On failure: one retry with
  the offending names listed, then fall back to `_generate_scope_summary` (deterministic).
  Log verification failures to the journal — this is the summarizer's effective-FP meter.
- Freshness: a scope summary's digest input now includes child summary digests — extend the
  ADR-0008 hash composition so a leaf change re-materializes exactly its ancestor chain.

**Touches.** `ingester/__init__.py` (Phase 4 ordering + verification), `summarizer.py` (parent
prompt), `materializer` (no change — reads summaries as before), ADR-0008 amendment.

**Accept.** Portfolio root AGENTS.md describes the three projects' division of responsibility
without naming entities absent from the graph; editing one leaf file re-summarizes only its
ancestor chain (journal shows the count); suite green.

**Effort.** M. **Risks.** Parent prompts exceeding context on huge directories — cap children
per prompt by importance rank, note truncation in output.

## R4. Structural importance (PageRank) in `scoring.py` — adopt aider's recipe

**What.** A pure `importance()` computation over the structural edge family at ingest, stored
on the entity, used to select what survives into summaries and R1 sections.

**Why.** "What does the code treat as load-bearing" is the proven selection signal (Aider's
repo map — recipe verified from source; HippoRAG PPR +20% multi-hop; LocAgent). ADR-0015
centrality answers a different question (doc grounding) and deliberately excludes
`calls`/`imports`. See
[hierarchical-materialization §2](../research/2026-06-09-hierarchical-materialization-and-importance-ranking.md).

**Design.**
- `scoring.py`: `def importance(nodes: Iterable[str], edges: Iterable[tuple[str, str, float]],
  *, damping: float = 0.85, personalization: Mapping[str, float] | None = None)
  -> dict[str, float]` — pure, no I/O (NetworkX is already a dependency via the store; keep
  scoring pure by passing prepared edges in).
- Edge preparation (ingester-side, before upsert), aider's multipliers adapted:
  structural family only (`calls`, `imports`, `inherits`, `implements`, `contains` at 0.25);
  **×0.1 when target name starts with `_`** (private); **×0.1 when the target's bare leaf is
  defined in >5 files** (ambiguous — the resolver's `ambiguous_names` stat already knows);
  no sqrt-multiplicity term needed (the store dedups `(source, target, kind)`).
- Normalize to [0,1] by graph max; store as `Entity.importance: float = 0.0` (additive field,
  like `centrality`).
- Consumption: Phase-4 ranking becomes
  `ranking_weight(confidence, centrality, importance) = confidence × (1 + centrality) ×
  (1 + importance)`; R1 section caps rank by `edge_weight × confidence × (1 + importance)`.
- **A/B knob:** `CK_SCORING_IMPORTANCE_MEASURE = pagerank | indegree | off` — the
  PageRank-vs-in-degree question is genuinely open (no published ablation for LLM context
  selection); R2 decides it.
- **Scope-local personalization** (with R3): when ranking for scope S's file, put
  personalization mass on S's entities so the ranking is "important from S's vantage point."

**Touches.** `scoring.py`, `graph/protocol.py` (field), `lightrag_adapter.py` (serialize),
`ingester/__init__.py` (compute between resolution and Phase 4), `ontology.base.yaml` (no
change — policy stays in scoring defaults until measured).

**Accept.** `KnowledgeStore`, `Entity`, `resolve()` rank in the top decile of importance on
this repo; the knob flips measurably change Phase-4 entity ordering; R2 shows
non-negative delta vs. `off`.

**Effort.** S–M. **Risks.** Importance double-counting with centrality in the composite —
keep both as boosts (never gates) and let R2 sweep the composition.

## R5. Tenets — authored design rules distributed through the ontology

**What.** A `tenets:` block in `ontology.yaml` (base + overlays per ADR-0025 composition),
rendered into AGENTS.md; later, optional structural `check:` rules that turn tenets into
reflexion-model conformance findings.

**Why.** Human-authored, specific, non-redundant guidance is the *only* context-file content
class with a measured positive effect on agent success (+4 pts), and it is the cheapest
normative feature — distribution, not computation. The reflexion model (authored model vs.
extracted structure, divergences reported) is the 30-year-validated shape, and its known
weakness — the authored model going stale — is the kernel's home turf. See
[design-signals §5–6, §8.1–3](../research/2026-06-09-design-signals-normative-layer.md).

**Design.**
- Schema (base declares it; overlays carry instances, same as concepts):
  ```yaml
  tenets:
    git-io-single-module:
      text: All git I/O goes through context_kernel/change_detection.py — never call git elsewhere.
      scope: project            # or portfolio
      applies: "context_kernel/**"   # glob; tenet renders only in matching scopes
      check:                    # optional, phase 2
        kind: only-importer
        subject: "context_kernel/change_detection.py"
        forbidden_elsewhere: ["subprocess.*git", "import git"]
  ```
- Rendering: a `## Tenets` section near the top of matching scopes' AGENTS.md (after pinned
  blocks), **hard cap ~5 lines per scope** (`materializer.max_tenet_lines`) — the ETH result
  says unnecessary specification measurably hurts; enforce the budget, don't trust restraint.
- Authoring rules documented in the schema: tenets must be **scope-specific and falsifiable**
  ("X is the only writer to Y"), never aesthetic ("prefer deep modules") — agents over-obey
  generic style edicts.
- Tenet text participates in the composed-ontology hash (ADR-0024 §5 already specifies the
  mechanism) — a tenet edit re-materializes the matching scopes, nothing else.
- **Phase 2 — `check:` rules:** a small conformance pass at ingest evaluates declared checks
  against structural edges (`only-importer`, `no-import-from`, `single-writer`); divergences
  become findings in R7's signals view with the violating edge + `source_line` as receipt.
  Start with two or three check kinds; this is import-linter inside the graph.

**Touches.** `ontology.py` (schema + composition for `tenets`), `ontology.base.yaml`,
`materializer/templates.py`, later a `conformance.py` pass in the ingester.

**Accept.** A tenet authored in this repo's overlay appears only in its matching scopes;
editing it re-materializes exactly those scopes; total AGENTS.md token growth per scope ≤ the
cap; phase 2: a deliberately planted `subprocess git` call elsewhere produces a finding with
file:line.

**Effort.** S (phase 1), M (phase 2). **Risks.** Tenet sprawl re-creating the over-prescription
failure mode — the cap and the falsifiability rule are the guardrails; review tenet count at
each release gate.

## R6. Merge review queue → curated aliases (recall without losing determinism)

**What.** The resolver emits merge candidates; a materialized `views/merge-queue.md` presents
them pay-as-you-go ordered; operator verdicts land in ontology overlays as `altLabel`
(accept) or `distinct-from` (reject) and are re-applied deterministically on every ingest.

**Why.** Deterministic ER under-merges (canonicalization literature is unanimous); the fix
that preserves idempotency is persisting human verdicts as first-class inputs (Apple Saga's
quarantine model), queueing only where signals disagree (QBC/HUMO: human-on-the-gray-zone
gives bounded-cost quality guarantees). See
[ontology-and-entity-resolution §2](../research/2026-06-09-ontology-and-entity-resolution.md).

**Design.**
- `entity_resolver.resolve()` additionally returns `merge_candidates: list[MergeCandidate]`
  where the signals disagree:
  (a) cross-cluster pairs with embedding cosine ≥ `θ_review` (default 0.75) whose normalized
  names differ; (b) doc-only concept nodes whose name matches **exactly one** method leaf
  (ADR-0026's deferred merge); (c) collision-guard deferrals (noncode members left as concept
  nodes because no second signal agreed).
  `MergeCandidate = (left_id, right_id, reason, cosine, evidence_excerpts)`.
- Optional pre-filter: `Summarizer.judge_merge(left_desc, right_desc) -> bool` — EDC-style
  feasibility veto, content-addressed verdicts like `judge_aspect`, runs only on queued
  candidates (bounded), absent-judge → no-op. **Zero-shot, no in-context examples** (they
  measurably degrade small models).
- View: `views/merge-queue.md`, ordered by expected gain (`cosine × max(centrality) ×
  evidence-count`), each row showing names, sources, cosine, judge verdict, and one-line
  description excerpts, plus the exact overlay snippet to paste for accept/reject.
- Verdict storage in the project overlay:
  ```yaml
  concepts:
    turn-panel:
      altLabel: [TurnPanelResponder]     # accepted merge → alias-driven, deterministic
      hiddenLabel: [trn-panel]           # match-only strings, never rendered (new field)
  resolution:
    distinct-from:
      - [Client (src/api.py), Client (src/db.py)]   # cannot-link; queue never re-asks
  ```
- Loader applies aliases before clustering (fold surfaces into the cluster key) and
  `distinct-from` as cannot-link constraints (forbid cluster union). Both polarities persist;
  re-ingest is a pure function of source + curated constraints.
- A verdict whose justifying evidence changes (source content hash of either side's defining
  file) is flagged back into the queue rather than silently kept (Saga's re-validation rule).

**Touches.** `entity_resolver.py`, `ontology.py` (schema: `hiddenLabel`, `resolution:` block),
`summarizer.py` (`judge_merge`), `materializer` (view), `concepts.py`.

**Accept.** On the Ticket Agent corpus, the queue surfaces ≥20 candidates; accepting one via
overlay produces the merged node on next ingest with no other diff; rejecting one suppresses
it permanently; full re-ingest with the same overlay is byte-identical.

**Effort.** M. **Risks.** Queue noise → tune `θ_review` against verdict history (the queue's
own effective-FP rate is measurable from accept/reject ratios in the journal).

## R7. Design-signals view — the evidence-anchored attention queue

**What.** `views/design-signals.md`, operator-facing, computed at ingest from graph + git:
hotspots, change coupling, documentation gaps, depth outliers, pass-throughs — ranked by
`severity × hotspot-ness`, every flag carrying a receipt, with an effective-FP feedback loop.
Agent-facing promotion is per-signal-class and gated on measured precision.

**Why.** This is the PoSD layer made mechanical, in evidence order: churn-anchored composites
have the strongest validation (Code Red: 15× defects, +124% resolution time; process metrics
beat code metrics — near-consensus); change coupling is information leakage made measurable
and catches what static analysis can't (including code↔doc, cross-language); module
depth/pass-through have *no* published validation — the kernel pioneers, so it ranks
relatively and never sets absolute cutoffs. The governing risk is alert fatigue (Google: ≤10%
effective FPs, disable-don't-tune, **queue-in-workflow — dashboards failed twice**) and, for
agents, over-obedience. See
[design-signals](../research/2026-06-09-design-signals-normative-layer.md) throughout.

**Design.**
- `change_detection.py` gains `co_change(window: int = 200) -> dict[frozenset[str], tuple[int, int]]`
  — parse `git log --name-only -n {window}`, return co-occurrence and per-file counts. Safe
  default `{}` on failure, like everything else in the module.
- Signal computations (new `context_kernel/signals.py`, pure functions fed by ingester):
  - **Hotspot:** `relative_churn(f) × (1 + importance(module(f)))`, top decile flagged.
  - **Change coupling / leakage:** pairs co-changing in ≥70% of commits touching either,
    support ≥5, **and no structural edge between their scopes** — the no-edge condition is
    what turns co-change into an information-leakage signal. Receipt: the commit shas.
  - **Doc gap (churn-ranked):** `centrality × relative_churn × [no realizes/governed-by
    in-edge from a doc node]` — the existing gap concept, now ranked by heat.
  - **Depth outlier:** `interface_count / internals_loc` per module (both already extracted);
    flag bottom decile **∧** fan-in top quartile. Relative only; no absolute threshold exists
    to borrow.
  - **Pass-through:** method body = single call forwarding its own parameters with
    same/similar name (AST check in the Python/TS handlers); flag classes where ≥50% of
    methods delegate (Fowler's Middle Man rule). Receipt: the forwarding line as a CodeSpan.
- Rendering: ranked sections, each finding =
  `severity·hotspot score — claim — receipt (files:lines, numbers, commits) — suggested action`.
  Two modes: `--changed-only` (pre-commit moment: findings touching files in the diff — the
  in-workflow surface) and full (on demand).
- **Effective-FP loop:** each finding has a stable id; an operator verdict file
  (`.context-kernel/signal-verdicts.toml`: `id = "fixed" | "not-useful" | "later"`) feeds the
  journal. A signal class with >10% `not-useful` over a trailing window is **auto-disabled**
  with a loud log line.
- **Agent-facing promotion (explicitly later):** per class, only after the FP bar holds, and
  injected as evidence-anchored *observations* in AGENTS.md ("`a.py` and `b.py` co-changed in
  12 of 14 recent commits; no structural edge explains it — see views/design-signals.md"),
  never imperatives. R2 measures the effect — including refactor-churn attributable to
  promoted signals, not just precision. This would be the first data of its kind.

**Touches.** `change_detection.py`, `signals.py` (new), `ingester/handlers.py` (pass-through
detection), `materializer` (view + later observation injection), journal.

**Accept.** On this repo the view flags a known-plausible hotspot and at least one co-change
pair with receipts; `--changed-only` at commit time lists only findings touching the diff;
marking a class `not-useful` past threshold disables it on the next run.

**Effort.** M–L. **Risks.** True-but-unimportant flooding — the `× hotspot-ness` ranking is
the defense; if the operator stops reading the view, that *is* the effective-FP signal — act
on it (disable classes), don't tune in place.

## R8. Cross-project structural linkage — manifests first, contracts second

**What.** (a) A `ManifestHandler` (StructuredHandler) over `pyproject.toml` /
`package.json` emitting `external-package` entities and `depends-on` edges; sibling-project
matches become **cross-project project-level edges**. (b) Later, an `OpenAPIHandler` making
the API contract the deterministic join point between frontend and backend symbols.

**Why.** Concept hubs are the only cross-repo bridge today; real portfolios have
deterministic cross-project structure being dropped. External libraries having no node is
also the residual conflation source ADR-0026 measured (11.4% of `imports` landing on doc
prose). Name-based cross-language matching has no research support; **the contract artifact is
the production-standard anchor** (FastAPI → openapi.json → openapi-typescript). See
[ontology-and-entity-resolution §5](../research/2026-06-09-ontology-and-entity-resolution.md).

**Design.**
- Ontology: new structural kind `external-package` (closed family, parser-emitted); reuse the
  existing `depends_on` edge kind — **and fix its naming**: the YAML handler emits
  `depends_on` (underscore) where every other kind is hyphenated; normalize to `depends-on`
  with a re-ingest migration (ADR-0008).
- `ManifestHandler.extract()`: parse `[project.dependencies]` / `dependencies` +
  `devDependencies`; emit one `external-package` entity per dependency
  (`name`, version-spec in description) and `module(project root) —depends-on→ package` edges.
- Resolver: `imports`/`calls` endpoints that fail code resolution but match an
  `external-package` name bind there (closing ADR-0026's residue deterministically) instead
  of falling through to doc prose or dropping.
- Portfolio post-pass in `ingest_portfolio()`: a dependency whose normalized name matches a
  **declared sibling project** (the config's project list — no guessing) becomes
  `projectA —depends-on→ projectB` between the projects' root module nodes, flagged
  `cross_repo` (the export layer already supports the flag).
- Render in R1's sections at project/portfolio altitude: the portfolio root AGENTS.md gains a
  deterministic project dependency table.
- **Phase 2 — `OpenAPIHandler`:** `operation` and `schema` entities from
  `openapi.{json,yaml}`; `exposes` edge to the backend handler (FastAPI operationId ↔ function
  name — exact match only, never fuzzy); `consumes` edge from frontend call sites where the
  generated-client import is structurally identifiable. Exact-match-or-drop, per ADR-0017's
  stance.

**Touches.** `ontology.base.yaml`, new handler(s), `entity_resolver.py` (external-package
binding), `ingester/__init__.py` (portfolio post-pass), `graph_export.py` (already has
`cross_repo`).

**Accept.** Portfolio AGENTS.md shows `evergreenlabs-bot —depends-on→ evergreenlabs` iff the
manifest declares it; `imports anthropic` binds to an `external-package` node, not a
`constraint` doc node; cross-project edge count > 0 without any entity merging (non-goal 2
intact).

**Effort.** S (manifests) + M (OpenAPI). **Risks.** Monorepo-style path dependencies and
aliasing — start with exact name matches against the declared project list only.

## R9. Ontology evolution guardrails — holding pen and release gate

**What.** Out-of-vocabulary kinds the extractor emits go to a materialized **proposed-kinds
holding pen** instead of silently into the weighted graph; vocabulary changes are accepted in
batch "release" commits; the composed kind-count gets a budget warning.

**Why.** Unconstrained LLM extraction proliferates kinds (EDC: 529–667 self-generated where
~200 sufficed); extraction reliability degrades measurably as the label space grows (safe
band: single-digit-to-low-teens kinds per prompt) — ADR-0025's union-add could quietly walk a
project's composed prompt out of the band. Production vocabularies survive on stable IDs +
batch editorial gates (SKOS/Getty/LoC). See
[ontology-and-entity-resolution §4](../research/2026-06-09-ontology-and-entity-resolution.md).

**Design.**
- Today's `log.debug("…accepting anyway")` path additionally records
  `(kind, count, example extraction)` per run; materialize as a section of
  `views/ontology-proposals.md` with frequency counts and ready-to-paste overlay snippets
  (same UX as R6's queue).
- `compose_ontology()` warns loudly when a project's composed semantic-kind count exceeds
  `ontology.max_prompt_kinds` (default 15) — warn, don't fail (errors-out-of-existence).
- Document the release-gate convention in the ontology schema: vocabulary edits land as
  deliberate overlay commits (the composed-ontology hash already scopes the re-extraction
  blast radius per ADR-0025 §5); kinds are deprecated, never deleted; renames keep the old
  name as a hidden alias.

**Touches.** `summarizer.py` (record OOV kinds), `ontology.py` (budget warning),
`materializer` (view).

**Accept.** A doc chunk eliciting an undeclared kind shows up in the proposals view with a
count, and its edges carry `edge_weight_default` until promoted; composing >15 kinds warns.

**Effort.** S. **Risks.** None material — this is instrumentation on existing behavior.

## R10. Housekeeping batch — truth, speed, and budgets

**What.** Four small corrections, one PR.

1. **Rename `LightRAGStore` → `JsonGraphStore`** (keep an alias for one release) and amend
   ARCHITECTURE.md §1.1/§2.1: the shipped store is hand-rolled JSON+NetworkX; LightRAG's
   machinery was never used (ADR-0017 established this; the architecture doc still claims
   pluggable Neo4j/Postgres/Milvus). The doc-drift system should not carry drifted docs.
2. **Vectorize `_cosine_sim`**: load chunk embeddings into one numpy matrix at store init
   (`float32`, rows L2-normalized); `search_similar` = single matvec + `argpartition(k)`.
   Pure-Python unpack-and-loop is in the `find` hot path and won't survive the method-node
   growth (+37% entities).
3. **ADR-0020 revisit note:** drift currently covers only doc→code edges; doc→doc claims
   (ADR superseding analysis, THEORY referencing ADRs) accrue none. Record as a known limit.
4. **Path token budget:** the CLAUDE.md bridge auto-loads every AGENTS.md on the walked path,
   so budgets are additive. Materializer computes cumulative root→leaf tokens; `ck check
   --budget` warns when any path exceeds `materializer.max_path_tokens` (default 8k; per-file
   target 1–3k per the context-rot evidence). R1/R5 sections count against it.

## Negative recommendations — do not build

- **No runtime synthesis, still.** LazyGraphRAG's economics don't transfer (no LLM at read
  time is the kernel's regime and Zep's latency evidence supports it); the response to any
  "needs synthesis" feature remains a new materialized view.
- **No per-function complexity metrics.** Cyclomatic ≈ LOC; cognitive complexity unproven for
  defects; LCOM/Henry–Kafura empirically dismantled. LOC + churn + structure carry the signal.
- **No inline embedding/LLM auto-merge in the resolver.** Every strong system uses embeddings
  as a gated secondary signal; auto-promotion without a human gate is precision drift
  (AutoKnow's regime needs behavioral logs a personal kernel lacks). R6's queue is the
  channel.
- **No generic PoSD sermons in agent context.** Agents over-obey; aesthetic tenets induce
  churn. Tenets are scope-specific and falsifiable or they don't ship.
- **No public benchmark as the primary eval.** Contamination + task defects (SWE-bench
  Verified post-mortem); the private paired suite is the instrument.
- **No semantic-kind growth past the low teens per composed prompt** without R9's gate —
  extraction quality measurably degrades with label-space size.
- **No standing global dashboard for signals.** Queue-in-workflow at the commit moment,
  scoped to changed files; dashboards failed twice at Google scale and will fail faster for
  one person.
- **No new graph backend work.** The JSON+NetworkX store with a numpy index is comfortably
  inside budget at portfolio scale; backend swaps are a deferred mechanism behind the existing
  protocol, not a need.
