This scope defines the design and documentation for the Context Kernel system — a pull-based, just-in-time context materialization pipeline that ensures an AI coding agent always reads fresh, coherent project knowledge. The system solves the problem of stale or fragmented context by making regeneration a precondition of every read: before any materialized file (AGENTS.md or view) is returned to the agent, a freshness check compares graph and source-tree hashes against the file's header, triggering automatic regeneration on mismatch. No daemon, file watcher, or background process exists — the first read after a source change pays the regeneration cost, and subsequent reads return cached files.

The primary agent-facing interface is a tree of materialized markdown files on disk, accessed via standard Read/Grep/Glob tools. A narrow stdio MCP server provides two read-only orientation tools (`overview` and `find`) that point the agent at these files, but holds no independent index, cache, or session state — it is a pure read-through over the on-disk materialized tree. All mutation goes through the `ck` operator CLI (`ck ingest`, `ck materialize`, `ck check`, `ck mcp`), which is the only writer to the `.context-kernel/` directory. The MCP server is spawned per session via stdio transport and automatically launched by the harness when Claude Code spawns in the root directory.

The system's architecture follows several key design patterns. The graph is the single source of truth; materialized files are derived views that are never authoritative. Hand edits are only preserved inside `<!-- pinned -->` blocks, which become inputs to the next regeneration — free-form edits outside those blocks are overwritten without warning. Every module hides a decision likely to change: the graph backend behind a Parnas seam defining read/write shape including `graph_commit()`, `get_entity()`, `get_neighbors()`, and `upsert()`; the summarization and embedding models behind abstract interfaces hiding changes between Qwen3 variants or cloud models; and the MCP transport behind a seam that could switch from stdio to Streamable HTTP for multi-editor scenarios.

The design document resolves several architectural decisions before coding begins. The essential problem is right-scoped knowledge for the agent; everything else is implementation that must be hide-able. Mutable state is concentrated in one place (the graph), with embeddings, summaries, and other derivable artifacts being content-addressed and immutable, making re-derivation cheap and garbage collection a sweep. The MCP server must never expose write tools, hold independent state, or return synthesized text not derivable from the on-disk materialized tree. Unresolved issues include the exact behavior of pinned-block merge semantics, the token budget for overview summaries (~2k tokens plus a '## See also' section), and whether supporting agents other than Claude Code (Cursor, CI agents) is a v1 requirement — with a git pre-commit hook running `ck materialize` as a slower but universally compatible fallback for freshness enforcement.
