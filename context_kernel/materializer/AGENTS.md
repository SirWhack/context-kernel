The materializer is the sole writer to the materialized tree — it owns the responsibility of producing every file that lives under a scope’s `.context-kernel/` directory. Its primary entry points are `materialize()` and `materialize_view()`, both exported from `__init__.py`. `materialize()` accepts a `ScopePath`, a `KnowledgeStore`, a tree root path, and a config object, then writes `AGENTS.md` and a thin `CLAUDE.md` bridge for that scope, returning the list of paths written. `materialize_view()` does the same for cross-cutting views, writing them under `.context-kernel/views/` according to a `ViewSpec`. Both functions follow a consistent pipeline: they render a `FreshnessHeader` (graph commit hash, source tree hash, and timestamp), extract any existing `<!-- pinned -->` blocks from the previous file, generate the new content via the templates module, merge pinned blocks back in, and finally write only if the content has changed (via the private `_write_if_changed` helper).

The public API is organized into several focused submodules. `headers.py` defines the `FreshnessHeader` dataclass and its `render()`/`parse()` functions, which implement invariant 2 (every materialized file carries a freshness header). `pinned.py` provides the `PinnedBlock` dataclass, `extract()` (which parses `<!-- pinned -->` blocks from existing files, returning blocks and warnings), and `merge()` (which re-inserts those blocks into freshly rendered output) — this is the only mechanism by which hand-edits survive regeneration. `templates.py` contains `render_agents_md()` and `render_claude_md_bridge()`, which produce the canonical markdown content for each scope. `reference_docs.py` offers `find_reference_doc()`, `detect_documentation_gap()`, `render_reference_pointer()`, and `render_gap_recommendation()` for linking to or recommending reference documentation per ADR-0014. `views.py` provides `render_view()`, which dispatches to private helpers `_render_index()` and `_render_by_topic()` to produce cross-cutting view content. All errors are surfaced via `MaterializationError`, a custom exception that carries the `ScopePath` and `GraphCommit` for debugging.

Internally, the materializer depends on the `KnowledgeStore` and `Summary` protocols from `context_kernel.graph.protocol`, the `ScopePath`, `ViewSpec`, `GraphCommit`, and `Sha256` types from `context_kernel.types`, and the `source_tree_hash` function from `context_kernel.change_detection`. It uses `pathlib.Path` for filesystem operations and `datetime` for timestamps. The design follows a pipeline pattern: each submodule handles one stage of the materialization process, and the `__init__.py` orchestrates them in order. The pinned block mechanism is the key architectural invariant — it ensures that operator edits inside `<!-- pinned -->` markers are preserved across regenerations, while everything else is overwritten.
